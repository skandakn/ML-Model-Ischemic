Executive Summary

Phase 11 performed a formal production deployment hardening, environmental security audit, and runtime architecture evaluation of the BeatAhead platform. The objective was to ascertain whether the current staging integration—which successfully pairs the Next.js web application (C:\ischemic) with the frozen Python machine learning inference service—is operationally viable for direct serverless deployment to Vercel.

Key Finding: Deployment Blocker Identified

A critical architectural blocker was identified: The Next.js staging integration in src/app/api/ml/predict/route.ts relies on connecting to a persistent local Python daemon (http://127.0.0.1:8000) and falls back to a synchronous child process invocation (execFileSync) pointing to local Windows directory paths (C:\ML Model - Ischemic\.venv\Scripts\python.exe).

In a standard Vercel production deployment: 1. No Persistent Daemon: Vercel executes Next.js API routes inside ephemeral, stateless Linux serverless microVMs; 127.0.0.1:8000 does not exist and connections will be immediately refused (ECONNREFUSED). 2. Local Path Invalidation: The fallback paths (C:\ML Model - Ischemic\...) do not exist in the Linux container filesystem (/var/task/). 3. Missing Python ML Environment: The standard Vercel Node.js runtime does not bundle Python, XGBoost, Scikit-learn, Joblib, or NumPy.

Therefore, direct deployment to Vercel (vercel --prod) will fail at the inference boundary. In accordance with Phase 11 instructions, this blocker is explicitly recorded and production deployment is strictly HALTED.

Failure Mechanism on Vercel Production

When deployed to Vercel without external service provisioning: - fetch("http://127.0.0.1:8000/predict"): Times out or throws fetch failed (ECONNREFUSED). - execFileSync("C:\\ML Model - Ischemic..."): Throws ENOENT (path not found) or EACCES on Linux. - Frontend User Experience: Returns 503 Service Unavailable with sanitized error code ML_SERVICE_ERROR. The web dashboard safely suppresses predictions, but live inference becomes non-functional.

5. API Security & Input Validation (Task 5)

The POST /api/ml/predict endpoint implements strict input sanitization: 1. Payload Type Enforcement: Rejects non-JSON payloads, arrays, and malformed strings with 400 Bad Request. 2. Schema Completeness: Validates that all 26 Matrix A features are present. Missing keys are rejected immediately with missing_features details. 3. Strict Bounds Checking: Every numerical feature is compared against physiologically plausible human ranges (FEATURE_BOUNDS). Impossible heart rates (e.g. 450 bpm) or corrupted voltages are rejected with 400 Bad Request. 4. Non-Finite Value Rejection: NaN, +Infinity, and -Infinity are rejected before reaching the inference model. 5. Timeout Protection: Upstream network requests to ML_SERVICE_URL enforce an explicit 2,000 ms timeout via AbortController, preventing worker thread exhaustion.
